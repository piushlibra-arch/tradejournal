# MyTradeJournal — Production Deployment Guide for Render

> **Trade. Review. Improve.**  
> Comprehensive operational guide for deploying MyTradeJournal on Render with a publicly accessible Next.js frontend, FastAPI backend, and persistent PostgreSQL database.

---

## 1. Production Architecture Overview

The deployed application follows a modular monolith architecture:

```
[ User Browser ]
       │
       │ (Public HTTPS)
       ▼
┌──────────────────────────────────────────────┐
│  Next.js 16 Frontend Web Service             │
│  (https://mytradejournal-frontend.onrender.com)
└──────────────────────┬───────────────────────┘
                       │
                       │ (Public HTTPS / CORS Restricted)
                       ▼
┌──────────────────────────────────────────────┐
│  FastAPI Backend Web Service                 │
│  (https://mytradejournal-backend.onrender.com)
└──────────────────────┬───────────────────────┘
                       │
                       │ (Render Private Network / TLS)
                       ▼
┌──────────────────────────────────────────────┐
│  Managed PostgreSQL 16 Database              │
│  (Private internal hostname:port)            │
│  Storage: Persistent SSD                     │
└──────────────────────────────────────────────┘
```

- **Frontend**: Next.js 16 (App Router), React 19, TypeScript, Tailwind CSS, Recharts, and TradingView Lightweight Charts. Hosted as a Node.js web service.
- **Backend**: Python 3.11, FastAPI, SQLAlchemy 2.0 Async, asyncpg, Alembic migrations, uv package manager, Uvicorn ASGI. Hosted as a native Python web service.
- **Database**: Render Managed PostgreSQL (version 16). Private network communication with backend; zero direct external access.

## 2. Render Blueprint Specification (`render.yaml`)

The repository includes a production-ready `render.yaml` at the root that provisions and wires all three components together in a single blueprint.

### Resources Defined in `render.yaml`:

| Resource Type | Resource Name | Plan | Region | Description |
|---|---|---|---|---|
| **PostgreSQL Database** | `mytradejournal-db` | `free` ($0/mo) | `oregon` | Render Managed PostgreSQL 16 (expires after 30 days) |
| **Web Service** | `mytradejournal-backend` | `free` ($0/mo) | `oregon` | FastAPI ASGI backend with Python 3.11, uv, and startup migrations |
| **Web Service** | `mytradejournal-frontend` | `free` ($0/mo) | `oregon` | Next.js 16 production server with Node 20 |

> [!NOTE]
> **Free Tier Characteristics**:
> - **Cost**: $0 / month (no credit card required).
> - **Migration Strategy**: Handled on server launch via `RUN_MIGRATIONS_ON_START: "true"` inside `backend/start.sh` (as Render Blueprints do not allow `preDeployCommand` on the free tier).
> - **Inactivity Sleep**: Free web services spin down after 15 minutes of inactivity; the initial request after sleep takes 30-50 seconds to warm up.
> - **Database Lifespan**: Render's free PostgreSQL database is valid for 30 days. To retain data permanently without expiration or sleep, change `plan: free` to `plan: starter` in `render.yaml`.

## 3. Step-by-Step Deployment Instructions

### Step 1: Push Repository to GitHub or GitLab
Ensure your code is pushed to your private or public Git repository:

```bash
git add .
git commit -m "feat: prepare MyTradeJournal for Render deployment"
git remote add origin https://github.com/<your-username>/mytradejournal.git
git branch -M main
git push -u origin main
```

*(Note: `.env` and `.env.local` files are excluded by `.gitignore` and will never be committed).*

### Step 2: Create Blueprint on Render
1. Log in to your [Render Dashboard](https://dashboard.render.com/).
2. In the top-right corner, click **New +** and select **Blueprint**.
3. Connect your Git repository (`mytradejournal`).
4. Select the `main` branch.
5. Render will automatically detect `render.yaml` in the root directory and display the three resources:
   - `mytradejournal-db` (Database)
   - `mytradejournal-backend` (Web Service)
   - `mytradejournal-frontend` (Web Service)
6. Click **Apply**.

Render will provision the database, build the backend, apply database migrations, build the frontend, and launch both services on HTTPS URLs.

## 5. Database Migrations

### Automatic Migrations (Starter Plan and above)
The backend `render.yaml` is configured with:
```yaml
preDeployCommand: uv run alembic upgrade head
```
Render runs this command on a single isolated instance before routing traffic to the newly built container. Existing application instances remain online until the migration finishes and the new build passes health checks.

### Manual Migrations (Render Web Shell)
If running on a plan where `preDeployCommand` is disabled or if a migration needs to be executed manually:
1. In the Render Dashboard, open the `mytradejournal-backend` service.
2. Click **Shell** in the left navigation.
3. Run:
   ```bash
   uv run alembic upgrade head
   ```
4. Verify the active revision:
   ```bash
   uv run alembic current
   ```

## 6. Health Checks & Monitoring

The application includes zero-credential-leakage health endpoints:

### 1. Backend Liveness (`/health`)
- **URL**: `https://mytradejournal-backend.onrender.com/health`
- **Purpose**: Verifies that the Uvicorn ASGI server and FastAPI event loop are accepting requests.
- **Configured in Render**: `healthCheckPath: /health`
- **Response**: `{"status": "healthy", "app": "MyTradeJournal", "environment": "production"}`

### 2. Backend Readiness (`/health/ready`)
- **URL**: `https://mytradejournal-backend.onrender.com/health/ready`
- **Purpose**: Runs a lightweight `SELECT 1` query via SQLAlchemy async connection pool.
- **Response (Connected)**: `HTTP 200` `{"status": "ready", "database": "connected"}`
- **Response (Disconnected)**: `HTTP 503` `{"status": "unhealthy", "database": "disconnected"}`

### 3. Frontend Health (`/api/health`)
- **URL**: `https://mytradejournal-frontend.onrender.com/api/health`
- **Purpose**: Verifies Next.js server runtime and SSR capability.
- **Configured in Render**: `healthCheckPath: /api/health`
- **Response**: `{"status": "healthy", "app": "MyTradeJournal Frontend"}`

## 7. File Uploads & Persistent Storage Architecture

### How Uploads Are Handled:
1. **CSV Broker Imports**: The frontend client reads CSV files directly in browser memory and submits them as structured JSON strings to `/api/v1/imports/preview` and `/api/v1/imports/confirm`. They are parsed and saved into the `trades` and `executions` PostgreSQL tables transactionally.
2. **Notes, Setups & Strategy Blueprints**: Stored in PostgreSQL `Text` and `JSONB` columns.
3. **Screenshots & Attachments**: Image URLs are validated and persisted in PostgreSQL `daily_journal_entries.screenshots` (JSONB) and `trade.notes`.

> [!NOTE]
> Because all trade records, import jobs, and configurations live directly inside the managed PostgreSQL database, **the web services are completely stateless**. Redeploying, scaling, or restarting backend and frontend containers causes zero data loss.

## 8. Database Backup & Disaster Recovery

### Managed Backups in Render:
- Render takes automated daily backups of managed PostgreSQL databases.
- Backups are stored in object storage and retained according to the selected plan tier.

### Manual Backup (CLI / Local):
To create an on-demand SQL dump from your machine:
```bash
# Retrieve the External Connection String from Render Dashboard -> Database -> Info
pg_dump "postgres://user:password@hostname.render.com:5432/tradejournal" -F c -b -v -f mytradejournal_backup_$(date +%Y%m%d).dump
```

### Restore Backup:
To restore into a database instance:
```bash
pg_restore -v -d "postgres://user:password@hostname.render.com:5432/tradejournal" --clean --if-exists mytradejournal_backup_20261024.dump
```

## 9. Secret Rotation Procedures

### Rotating `JWT_SECRET_KEY`:
1. In the Render Dashboard, navigate to `mytradejournal-backend` -> **Environment**.
2. Click **Edit** next to `JWT_SECRET_KEY` and enter a new 64-character random string (or delete it to regenerate via `generateValue`).
3. Click **Save Changes**. The service will automatically redeploy.
4. *Effect*: Users with existing active sessions will be prompted to re-authenticate on their next request.

### Rotating PostgreSQL Credentials:
1. In the Render Dashboard, open `mytradejournal-db`.
2. Go to **Settings** -> **Access Control** -> **Rotate Password**.
3. Render automatically updates the internal `connectionString` referenced in `render.yaml`.
4. Trigger a manual deploy of `mytradejournal-backend` to ensure the new connection pool takes effect.

## 10. Troubleshooting & Common Issues

### Issue 1: CORS Blocked Error in Browser Console
- **Symptom**: `Access to XMLHttpRequest at '...' from origin '...' has been blocked by CORS policy`.
- **Cause**: The frontend public URL is not in the backend `CORS_ORIGINS` variable.
- **Fix**: Open `mytradejournal-backend` in Render -> **Environment**, ensure `FRONTEND_URL` and `CORS_ORIGINS` match the exact frontend URL (e.g. `https://mytradejournal-frontend.onrender.com` without trailing slash).

### Issue 2: `ModuleNotFoundError: No module named 'psycopg'`
- **Symptom**: Backend crashes on startup with psycopg error.
- **Cause**: Render passes `postgres://...` or `postgresql://...` while SQLAlchemy async expects `postgresql+asyncpg://`.
- **Fix**: Already handled! `backend/app/core/config.py` contains an automatic field validator that converts `postgres://` and `postgresql://` into `postgresql+asyncpg://`.

### Issue 3: Next.js Frontend Still Calls `localhost:8000`
- **Symptom**: Network requests in production browser fail with `ERR_CONNECTION_REFUSED` to `http://localhost:8000`.
- **Cause**: `NEXT_PUBLIC_API_URL` was not set during `next build`.
- **Fix**: In Render, verify that `NEXT_PUBLIC_API_URL` is set in the frontend service environment variables. Trigger a **Manual Deploy** -> **Clear build cache & deploy** so Next.js inlines the production backend URL.

## 11. Application Rollback

If a bad commit causes an issue in production:
1. In the Render Dashboard, select the affected service (`mytradejournal-backend` or `mytradejournal-frontend`).
2. Click **Deploys** in the left menu.
3. Locate the last known good deploy.
4. Click the three dots `...` on that deploy and select **Rollback**.
5. Render immediately reverts to that image/artifact without re-running builds.
